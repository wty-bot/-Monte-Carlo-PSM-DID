# AI工具使用记录

## 一、文档用途

本文档用于系统记录本项目在各阶段如何与不同 AI 工具协作，包括：

- 使用了哪些 AI 工具与模型
- 当时的关键 prompt 或核心提问方式
- 各工具的主要输出
- 人如何判断、筛选、修改这些输出
- 最终哪些内容被采纳，哪些没有被采纳

本文档既服务于当前课程作业的 AI 使用说明，也作为后续各阶段持续追加的统一记录模板。

目标是让读者：

1. 基本复原当时的人机协作过程
2. 理解关键修改背后的判断逻辑
3. 看到 AI 在项目推进中的实际作用与边界

---

## 二、参与的 AI 工具与模型

本项目当前阶段实际涉及的 AI 工具 / 产品 / 模型如下：

| 工具 / 产品 | 使用方式 | 底层模型 | 当前主要用途 |
|:---|:---|:---|:---|
| `Claude Code` | IDE / Agent 协作 | `Claude Opus 4-6` | 读取仓库、审查文档、修改文件、搭建环境、执行工程操作 |
| `Codex` | IDE / Agent 协作 | `GPT-5.5` | 代码与工程辅助、文档整理、环境检查、仓库结构调整 |
| `Open Code` | 本地配置的辅助工具 | `Kimi 2.6` | 作为额外参考意见来源，辅助环境与实现思路判断 |
| `ChatGPT` | 聊天端 | `GPT-5.5` | 方法论审阅、PRD 覆盖度检查、公式与表达优化建议 |
| `Gemini` | 聊天端 | `Gemini 3.1 Pro` | 工程风险补充分析，尤其是参数尺度、共同支持与匹配失败风险 |

说明：

- 本项目不是“单一 AI 生成、直接照抄”的流程，而是“多工具给意见，人再做取舍”的协作流程。
- 不同 AI 的定位不同：有的偏执行，有的偏审阅，有的偏补充风险。

## 六、阶段一：确定项目宏观架构

### （一）产出PRD文档

#### 1、阶段目标

- 在正式开始项目之前，先把课程作业要求整理成一份清晰的项目需求文档。
- 明确项目要完成什么、边界在哪里、后续各阶段应围绕哪些核心任务推进。
- 避免后续执行过程中对课程要求理解不一致，或者在实现中逐渐偏离题目主线。

#### 2、使用的 AI 工具

- `Claude / Claude Opus 4-7`：用于根据课程作业原文和人工整理的大纲，起草 PRD 初版。
- `Codex / GPT-5.4`：用于对初版 PRD 做进一步审校和修改，帮助检查结构、表述和需求覆盖是否完整。

#### 3、关键 prompt / 提问方式

这一部分的协作不是直接把课程作业丢给 AI 让它自由发挥，而是先由人完成第一轮理解和拆解。

具体过程是：

- 先自己通读了一遍 `课程作业.md`，梳理课程要求。
- 在此基础上，先手动拆了一版需求大纲，明确项目大概要包含哪些部分。
- 然后把 `课程作业.md` 和这份人工整理的大纲一起提供给 chat 端的 `Claude Opus 4-7`，让它先起草一个 PRD 初版。
- 在得到初版后，再把它交给 `Codex`，使用 `GPT-5.4` 做审校和修改。

#### 4、AI 工具的主要输出

- `Claude Opus 4-7` 先基于课程作业原文和人工提纲，生成了一版较完整的 PRD 草稿。
- 这一步的主要作用不是替代人工判断，而是把已经拆出来的需求更系统地组织成文档结构。
- 随后 `Codex / GPT-5.4` 对这版 PRD 做了进一步检查和修改，重点是看任务拆分是否顺畅、表述是否足够清楚、是否存在遗漏或歧义。

#### 5、人工判断与修改

- 这一阶段最关键的判断仍然由人完成：先自己读题、自己拆需求，再把整理后的输入交给 AI。
- 这样做的原因是，课程作业本身并不复杂到必须完全依赖 AI 理解，但如果没有先做人工拆解，AI 很容易写出看起来完整、实际上重点不清的 PRD。
- 在 `Claude` 产出初版后，又经过 `Codex / GPT-5.4` 审校，做了一些细节和表述的微调。最后再由人通读一遍确认没有明显问题，才把这版 PRD 定下来。
- 因此这一部分不是“AI 从零生成需求”，而是“人先定理解框架，AI 协助整理成文，再由人确认收口”。

#### 6、最终采纳与落地结果

- 形成了项目的 `PRD.md` 版本。
- 这份文档的作用主要有两个：
  - 第一，明确项目需求，避免后续执行阶段偏离课程作业主线。
  - 第二，把原本较散的课程要求整理成可执行的项目语言，方便后续继续做通用规划、任务规划和代码实现。

### （二）产出通用规划文档

#### 1、阶段目标

- 在 `PRD.md` 已经明确项目需求的基础上，进一步形成一份面向整个项目的通用规划文档。
- 提前确定项目的总体技术栈、目录结构、阶段划分和文件组织方式。
- 为后续任务一到任务四的执行提供统一框架，减少边做边改结构带来的混乱。

#### 2、使用的 AI 工具

- `Codex / GPT-5.5`：以 plan 模式为主，基于已有 `PRD.md` 协助整理项目总体规划。

#### 3、关键 prompt / 提问方式

- 这一阶段不是重新讨论课程要求本身，而是把已经在 `PRD.md` 中确定下来的项目需求，进一步落成一份通用规划。
- 具体做法是，基于 `PRD.md` 让 `Codex` 在 plan 模式下先从全局视角整理项目后续怎么推进，包括项目结构、技术栈、阶段分工和不同类型文件的放置方式。

#### 4、AI 工具的主要输出

- `Codex` 先给出了一版面向整个仓库的总体规划草稿。
- 这份草稿重点帮助明确了几件事：
  - 项目统一使用什么技术栈；
  - 代码、数据、图表、文档分别怎么组织；
  - 任务一、任务二、任务三、任务四以及最终整合大致如何分阶段推进。
- 相比 `PRD.md`，这一份文档更偏执行准备，而不是任务需求说明。

#### 5、人工判断与修改

- 这一阶段的人工判断重点不是逐句修改，而是确认这份规划有没有真正起到总框架的作用。
- 保留了其中最有价值的部分：总体技术栈、目录结构、阶段任务拆分和文件组织原则。
- 没有让这份文档写得过细，避免它提前替代后续各任务自己的专项规划文档。

#### 6、最终采纳与落地结果

- 形成了 `docs/plans/通用规划文档.md`。
- 这份文档的主要作用是先把项目的共用框架定下来，包括：
  - 统一技术栈；
  - 统一目录结构；
  - 统一阶段划分；
  - 统一代码、数据、输出物和正式文档的组织方式。
- 它为后续任务一、任务二的专项规划和代码落地提供了总的参照框架。

### （三）完成项目脚手架搭建

#### 1、阶段目标

- 把项目先整理成一个可以继续往下做的最小可用仓库。
- 提前补齐环境、目录和基础说明，避免后面一边写任务一一边返工项目结构。

#### 2、使用的 AI 工具

- `Open Code / Kimi 2.6`：负责实际搭建项目脚手架、配置环境，并补齐项目初始目录和基础文件。
- `Codex / GPT-5.5`：在 `Kimi 2.6` 完成初版后负责复核，检查是否有越界内容，以及依赖和基础配置是否存在遗漏。

#### 3、关键 prompt / 提问方式

- 这一阶段的重点不是做任务实现，而是先把仓库骨架搭起来。
- 协作时主要围绕两个问题展开：当前环境和依赖是否已经齐全，以及在还没正式进入任务执行前，哪些内容现在可以先补，哪些内容不应提前做到任务阶段。
- 人工校对后发现kimi2.6生成了超出任务边界的内容，要求codex予以检查、修正。

#### 4、AI 工具的主要输出

- `Kimi 2.6` 先完成了一版脚手架和环境配置，补了基础目录和部分仓库级文件。
- 但这轮执行有两个问题：一是部分工作做得偏多，超出了当前阶段边界；二是做完之后仍有一些依赖和配置没有补齐。
- 后续 `Codex` 又做了一轮复核和修正，把越界部分收回来，并补上缺失的依赖和基础配置。

#### 5、人工判断与修改

- 人工最终确认，这一阶段只做基础准备，不提前进入任务一和任务二的业务实现。
- 因此没有直接照收 `Kimi 2.6` 的全部执行结果，而是把阶段边界重新收紧，再让 `Codex` 补做复核和修正。
- 最终保留的是对后续推进真正有帮助的基础结构、仓库说明和环境配置。

#### 6、最终采纳与落地结果

- 完成了项目脚手架、基础目录和仓库级说明文件的搭建。
- 补齐了原先遗漏的部分依赖和基础环境配置。
- 仓库被整理到可以正式进入后续任务实现的状态，同时避免把本该后置的内容提前写进来。

## 七、阶段二：实现任务一

### （一）产出任务一规划文档
#### 1、阶段目标

- 在 `PRD.md` 和 `课程作业.md` 的基础上，形成一份能直接指导任务一实现、并能衔接后续任务二的规划文档。
- 这一阶段不是让 AI 从零设定模拟题材，而是先由人工给出模拟背景的核心设定，再让 AI 在这个基础上把任务一规划具体化。
- 保证课程要求不走样，同时保留统一主题、场景背景和理论解释线索，方便后续写任务三和研究报告。

#### 2、使用的 AI 工具

- `Claude Code / Claude Opus 4-6`：负责阅读文档、提出结构化审查意见并协助修改 `任务一规划文档.md`。
- `Codex / GPT-5.5`：辅助检查文档逻辑、结构一致性和任务边界。
- `ChatGPT / GPT-5.5`：补充方法论和课程要求层面的审阅意见。
- `Gemini / Gemini 3.1 Pro`：补充共同支持、参数强度和匹配失败风险方面的提醒。

#### 3、关键 prompt / 提问方式

- 这一阶段先围绕一个核心问题展开：在读取 `PRD.md`、`课程作业.md` 和现有 `任务一规划文档.md` 后，判断这份规划是否足以支撑任务一实现。
- 在交给 AI 之前，人工已经先给出模拟背景的核心设定：以环境监管政策变化对企业绿色投资的影响作为统一主题，并先想好各场景的大致方向，再让 AI 在这个前提下补足任务拆分、公式表达、参数口径和文档结构。
- 后续又逐步追加了几个明确修改点：500 次 Monte Carlo 循环归属、场景 B / C 公式表达、处理组规模约 300 家、文档结构精简，以及统一主题和场景说明的恢复。

#### 4、AI 工具的主要输出

- `Claude Code` 和 `Codex` 主要识别出四个问题：500 次 Monte Carlo 循环一度被写到任务二；场景 B / C 的趋势异质性一度写成处理后跳跃而不是斜率差异；处理组约 300 家与初版 logit 设定不完全一致；文档精简后一度丢了统一主题、现实背景和场景说明。
- 在此基础上，文档被逐步改成：任务一负责 3 个场景且每个场景运行 500 次 Monte Carlo 循环，统一参数和输出字段，明确场景 A / B / C 的 DGP，并区分正式输出与调试输出。
- `ChatGPT` 的反馈重点是：500 次循环必须写清；场景 B / C 要明确体现趋势斜率差异；处理组规模应统一到约 300 家；参数表、流程和验收标准要一致；任务二的匹配细节不要提前写死；文档不能因为精简而失去可解释性。
- `Gemini` 的反馈重点是：场景 B / C 可能存在共同支持和匹配失败风险，高 `X` 尾部尤其要警惕；`κ_i = 4` 可能偏强，适合留到预测试再看偏误和方差；还应区分共同支持不足和不可观测混淆这两类不同问题。

#### 5、人工判断与修改

- 最前面的核心设定来自人工而不是 AI，包括研究主题是政策变化与绿色投资，各个场景也先有人为设想，再交给 AI 去整理成可执行的任务一规划。
- 对 `PRD` 的硬要求直接采纳，特别是任务一必须完成 500 次 Monte Carlo 循环。
- 对 `κ_i = 4` 这类风险提示不立即按直觉改参数，而是保留到后续预测试阶段再判断。
- 对趋势异质性从处理前就开始的设定，先保留原识别思路，再通过解释文字补清含义。
- 对统一主题、现实背景和场景说明，最终确定必须补回文档，不能只留下技术框架。

#### 6、最终采纳与落地结果

- 最终形成了 `任务一规划文档.md`，核心内容包括：统一研究主题为更严格的环境监管政策对企业绿色投资的影响，统一现实背景为第 4 年开始实施更严格监管，三个场景共用统一数据外壳但 DGP 不同。
- 三个场景的出发点也被保留下来并写清楚了：有的是近似随机进入监管，有的是由可观测特征影响进入监管，有的是由不可观测因素影响进入监管。
- 每个场景都补齐了现实对应、处理分配、结果生成、识别意图和场景说明。
- 同时明确了任务一负责 500 次 Monte Carlo 循环、调试字段与正式字段的边界，并把共同支持检查纳入自检；`κ_i` 暂不提前调弱，保留到后续预测试再决定。
- 本阶段主要涉及 `任务一规划文档.md`、`PRD.md` 和 `课程作业.md`。

### （二）产出任务一代码实现与测试
#### 1、阶段目标

- 根据 `任务一规划文档.md` 实现 3 个场景的 DGP 和完整的 Monte Carlo 生成流程。
- 每个场景独立随机种子、独立运行 500 次，共生成 `3 × 500 × 1000 × 6` 条面板记录。
- 同时产出调试版和正式版数据，并完成处理率、共同支持和 `Y(0)` 趋势等自检。

#### 2、使用的 AI 工具

- `Claude Code / Claude Opus 4-6`：负责读取规划文档、重写任务一代码、执行模拟和运行自检。

#### 3、关键 prompt / 提问方式

- 这一阶段的执行起点很明确，就是先按顺序读取 `PRD.md`、`通用规划文档.md` 和 `任务一规划文档.md`，然后直接按照规划实现任务一。
- 重点不是先堆说明文件，而是先把 DGP、批量生成、自检逻辑和正式版 / 调试版双版本输出完整做通。

#### 4、AI 工具的主要输出

- `Claude Code` 最终新建了 `src/utils/paths.py`、`src/utils/seeds.py`、`src/simulation/dgp.py` 和 `scripts/run_task1_generate.py`，分别负责路径管理、独立随机种子、三场景 DGP，以及批量生成和自检。
- 三个场景的实现口径被正式写进代码：场景 A 为 `D_i ~ Bernoulli(0.3)` 且 `κ_i = 0`；场景 B 为 `p = logit^{-1}(-0.95 + 0.8*X_i)` 且 `κ_i = 4*X_i`；场景 C 为 `p = logit^{-1}(-0.95 + 0.2*X_i + 0.8*U_i)` 且 `κ_i = 4*U_i`。
- 生成脚本支持 `--n-sims` 和 `--check-only`，会同时输出正式版 parquet、调试版 parquet、共同支持图、`Y(0)` 趋势图和 Markdown 自检报告。

### 4. AI 工具的主要输出

- 多轮生成和重写 `reports/研究报告.md`，逐步补入：
  - 研究背景和场景说明
  - 模拟设计与方法设定

  - 结果展示的组织顺序

### 5. 人工判断与修改

这一阶段最终是以人工主导写作为主，AI 主要起到辅助整理、补句、压缩和局部润色的作用。

具体人工判断包括：

- 认为 AI 起初生成的“问题背景”虽然形式完整，但没有真正写清政策故事、场景含义和研究问题，因此由人手动重写背景和模拟设计
- 认为 AI 初版“结果展示”只是机械罗列表图，没有形成论文式链条，因此要求重写为：
  - 先总览结果
  - 再用估计分布图说明偏误不是偶然波动
  - 再用识别诊断解释 B 和 C 为什么分化
  - 最后补共同支持
- 认为 AI 早期生成的“理论解释”过于像答题提纲或教材复述，因此大量删除原文，由人重新组织和改写六个问题的回答
- 对研究口径做出关键修正：报告不再写成“研究政策是否有效”，而改为“在已知真实效应的模拟环境中研究方法识别能力”
- 对图表规范做出统一要求：图题和表题都放在对象下方；结果展示必须围绕图表展开，而不是让读者自己看图表
- 在 AI 提供了局部补写版本后，不直接照搬，而是只选取其中部分句子和数字口径作为参考，再由人自行改写并纳入正文
